线上样本 UTC 时间：2026-11-10 20:38:27.979593 发送，20:39:33.242570 看见首段，20:40:39.277018 收到完成状态。因此首段 **65.263 秒**，完成 **131.297 秒**。这是一个实际样本，不是延迟分位数或与历史 152 秒请求的同条件对照。

联调发现并修复两个实际阻断：签名原生文字误入 QQ 内容准入；长时间流式生成没有沿用原续租操作，加上细碎增量重复执行昂贵校验。最终实现仍在写事务中完成全部有效性校验，再通过已有队列续租；只合并有界队列中已缓冲的相邻正文片段，保留推理、工具及完成边界。

第一份联调脚本在成功回复后手动关闭 SQLite，遇到未完成的界面已读回执，未通过其进程内清理步骤。因此重启验收改为独立新进程并通过；未重复调用模型。独立服务端核对脚本首轮在生成结果时发生局部变量覆盖，保留失败日志后修正为只读核对并通过。原始私有记录及失败样本保留，不进入公开源码或分发包。

合成流式检查在供应商首段后暂停，直到客户端确实看见 RUNNING 正文预览并重连，再允许供应商结束；最终一轮、一次调用，重启恢复原消息。没有启动 QQ/Bridge 或付费供应商。回归还覆盖授权失效、EOF 保留 UNKNOWN、遗忘回放、过期租约、旧帧不能复活撤回/完成内容，以及每个 Bot 的密钥、缓存、队列与预览隔离。最终成功仍取决于原费用与 Outbox 事务。

## 性能范围与交付

本轮减少相同校验边界内的重复账本解析、复制，并在无关提交后做一次新鲜批处理重试；持续并发时仍保留保守回退。合成材料 1,000 条、约 2.27 MB，九次读取解析次数 9 → 1，无关提交中位数 8.90 → 5.91 ms；这是权限材料微基准，见 [隔离对照](performance-source-validation.md)。超过 16 MiB 的材料仍全量解析，财务检查点和完整回放优化另行验收。

**生产链路已经可用，但首段和完成延迟仍偏高。** 本次上下文构建约 18.38 秒，模型请求计时约 65.48 秒，其中包含传输、流消费和校验开销，不能全部当成供应商推理时间；模型结束后到任务完成还有约 29.42 秒。后续根据同条件样本继续优化，不能把原生投递或流式展示等同于低延迟。

交付目录 `.local/deliverables/native-chat` 包含 Windows x64 完整压缩包、Android 调试 APK、Core wheel / 源码包、SHA-256 manifest。Windows 需分发完整目录及依赖文件。已在本机登记的设备与历史保留；启动客户端后选择 Core，使用现有主人凭据登录。其他设备按原签名登记流程授权。

客户端支持同时连接多个独立 Core Bot 私聊。AstrBot、DSH、群聊、Android 后台通知及真机兼容仍为后续切片。
